## What software-factory literature is the Michelin-kitchen metaphor answering?

### Takeaway
The metaphor is a **rejection of the early-2026 “software factory / dark factory” pole**, not a rename of one product. The pole she is pushing off is: agents write and merge without humans reading code (StrongDM’s two rules, February 2026; Dan Shapiro’s level 5 “dark factory,” 23 January 2026, popularized by Simon Willison on 7 February 2026). On the same stream the host contrasts her method with Andrej Karpathy’s original vibe coding (2 February 2025): she keeps code and environment central, and she samples rather than never tasting. She also shrugs off “company brain” and “context graph,” and she hedges her own “inner loop / outer loop” wording.

### Inferences

## Which implementation primitives repeat, as design requirements?

### Takeaway
Repeated, sourced requirements are: a constrained codebase the agent cannot easily violate; a verification loop with real UI hands; deterministic tools extracted out of prose skills; markdown skills mined from corrections; an inner coding loop against a snapshot of intent; an outer trigger loop from chat/ticket systems; a coordinator that delegates and groups work; a buffer before bulk fixes; sampled post-merge review that edits the environment; and, on the factory side she is revising, holdout scenarios and behavioral checks the coding agent cannot rewrite. Worktrees were not found in these sources.

### Cited Findings
Each line is a design requirement a harness “in this spirit” would need, tied to who actually said it. Do not merge Tan’s stack with StrongDM’s stack into one architecture.

- **Environment constraints beat more prompting.** Turn repeated agent failures into lint rules, types, or structure so the bad path is unavailable. Tan, captions 26:17, 29:22, 31:46. https://postgrok.com/sources/2026-10-05-youtube-poteto-software-factory
- **Framework conventions as the constraint surface.** Directory-per-feature, restrictive lints, Next.js-like Electron framework, explicitly so the agent stops spending judgment on structure. The thing she calls Dune. Caption 30:10, motivated by ~8 god files of ≥10,000 lines (31:29). Same URL.
- **Verification is the skill that makes a loop a loop.** The agent must run the code, use it as a user would, and take traces and snapshots (“hands and eyes”). Without that, the human stays the proxy. Caption 16:24–17:50. Same URL. She says every Cursor or xAI app has an auto-maintained verification skill (19:10).
- **Autopilot means a verifier swarm, not an unread merge.** Full autopilot “spawn[s] a bunch of verifier agents for every pull request” and fuzzes by running the app and clicking; tunable from about ten verifiers to one. Caption 52:50. Same URL.
- **Extract deterministic work into code; leave judgment in the skill.** A skill is a thin wrapper around custom tools. Her verification skill contains a CLI that is “glue” over Playwright and the Chrome DevTools Protocol, because otherwise every agent rebuilds verification differently. Mechanical refactors (migrations) should be AST codemods, not agent reasoning. Captions 21:08–23:42. Same URL.
- **Skills are versioned process, in markdown, and should get smaller.** Mine your own correction prompts. She names a pstack skill, recall, that pulls forward context she used to retype. Captions 1:00:40–1:03:47. Same URL. Public tree Postgrok points at: https://github.com/cursor/plugins/tree/main/pstack (contents of the tree were not re-read here).
- **Inner loop: agents implement toward a snapshot of intent.** She identifies Cursor projects with this loop. The snapshot goes stale. Captions 35:32 and 44:03. https://postgrok.com/concepts/inner-outer-loop-agents
- **Outer loop: triggers, not a context graph.** A Slack MCP or a channel subscription; on a bug report the bot reproduces it with verification skills, confirms it on main, and files it into a Cursor project. Grok bots also watch X, email, and Linear on routines. Captions 36:51, 42:13, 38:22. Same URL.
- **Coordinator / subagents.** A Cursor project is a cloud agent with its own computer that “doesn’t do the work itself. It delegates and orchestrates.” On a burst of ~30 related reports it picks a topology. One agent per bug loses the cross-report thread and can duplicate work. Captions 42:52–44:33. Same URL.
- **A buffer or queue before fixing.** A scheduled scanner appends React footguns to a document; a human looks every couple of days so identical issues become one pattern. Pure per-bug execution misses the higher-level bug. Captions 47:40–48:22. Same URL.
- **Human review is sampling plus environment edits, including after merge.** Taste some dishes; if many agents share a workaround, change skills, lints, or types; revert or modify from commit history. Captions 49:34, 50:33, 52:45. https://postgrok.com/concepts/michelin-kitchen-metaphor
- **Trust is earned by the above, not by opening more agents.** Postgrok’s summary of her ladder: from micromanaging one agent, to the agent checking its own work, to many unattended. Bottleneck quote, caption 7:17: the bottleneck is no longer the agent but “your ability to express your intent.” https://postgrok.com/sources/2026-10-05-youtube-poteto-software-factory . A secondary recap of the September talk argues the same ordering: trust, then parallel. https://redreamality.com/blog/lauren-tan-poteto-trust-before-parallel/
- **Secondary ladder from a recap of the 21 Sept 2026 X talk** (not the Pocock captions; do not treat as her wording): five places to fix an agent mistake, chaptered from #5 human review, #4 skills, #3 rules and review bots, #2 checks that fail the build, #1 change the soil. The video description’s later numbered list does not match that chapter order, so the order is uncertain without the video. https://www.youtube.com/watch?v=tZbGWRdlkIs citing https://x.com/poteto/status/2102050467505430555
- **StrongDM requirements, only if imitating the factory pole rather than Tan:** specs as the human artifact; scenarios stored where the coding agent cannot edit them (holdout); LLM-judged satisfaction instead of only boolean tests; digital twins of dependencies; a non-interactive phase graph (Attractor) the human does not steer mid-run; a context store for transcripts and tool output (CXDB); humans do not write or review the code. https://simonwillison.net/2026/Feb/7/software-factory/ and https://factory.strongdm.ai
- **Shapiro level 4 requirements, the nearest published “leave the agents working” checklist she resembles:** write a spec, argue about the spec, craft skills, review plans, leave, check whether tests passed. Level 5 drops the human check. https://www.danshapiro.com/blog/2026/01/the-five-levels-from-spicy-autocomplete-to-the-software-factory/
- **Generic harness parts repeated in 2026 harness explainers, not claimed by Tan:** agent loop, tools (shell, edit, web, MCP), context trimming, memory that survives the session, instruction files (AGENTS.md / CLAUDE.md), permission and sandbox policy, a plan/todo the model updates, subagents. https://mljar.com/blog/ai-agent-harness/ and https://vercel.com/i/agent-harness

### Inferences
- A Grok-model harness “similar to michelin-kitchen or dune” that stays faithful to the sources has two layers. Layer A, Dune-like: the target repo is a strict framework (feature directories, lints, types) whose job is to make bad edits fail closed. Layer B, kitchen-like: skills plus a verification CLI, a coordinator that does not implement, an outer watcher that files reproduced bugs, a queue so fixes are batched by pattern, and a human who samples merged work and edits the kitchen. Layer B is the harness. Layer A is the codebase the harness is allowed to touch.
- StrongDM’s holdout scenarios and twins are the prior art for “verification the agent cannot cheat,” which is the same problem Tan points at when she says in-loop tests are not enough and the agent must use the real UI. They are not described as part of Dune or pstack.
- “Checks that fail the build” shows up in the secondary September-talk recap and is consistent with her lint-rule comments, but the five-rung ordering is not stable across that video’s own description. Prefer the Pocock captions for her hierarchy: verification first, then determinism extraction, then environment constraints, with human sampling last rather than as the main fix.

### Gaps
- **Worktrees, git isolation, and per-agent branches** are not described in the Tan, StrongDM (as quoted), Shapiro, MLJAR, or Vercel sources read here. Do not add them as her design.
- **Permission tiers and sandbox policy** are in the generic harness explainers, not in the Dune or kitchen captions.
- **Ticket system of record:** she names Linear, Slack, X, email, and Cursor projects. She does not describe a custom ticket schema, PR template, or memory file format.
- **Eval suites in the Hamel Husain sense** (datasets, graders, error analysis) are not cited. Her “verification” is runtime use of the app, traces, snapshots, and fuzzing clicks, plus lint. Her “sampling” is a human reading some merged PRs. Those are not the same artifact as an offline eval harness.
- pstack’s actual skill files were not opened, so skill names beyond verification, recall, and the caption mentions of a “how” skill and an “unslop” skill are not listed.
- No measured quality number (defect rate, revert rate, fraction of PRs she actually reads) was found for the 2,000–2,500 PR claim. She herself says many are gardening, not features.
