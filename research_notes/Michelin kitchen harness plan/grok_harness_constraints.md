## What is in google_harness_2_v1.0 at a directory and README level, and what loop does it implement?

### Takeaway

There is no root README; the runnable tree lives under a gitignored worktree.

- `controller.run_task` compiles a LangGraph `StateGraph` with nodes `references` → `proposals` → `probes` → `compose` → `finals`, then either loops to `proposals` (sequential mode while `round <= k`) or goes to `select` → `END`. References roll the base bundle `k` times and fail if none deliver. Proposals edit scopes `INV` and `DOM`. Probes execute those candidates. Compose edits scope `COMPOSE`. Finals execute compositions and advance `current` to the last composition. Select chooses only delivered completed records; the practical profile also makes baseline executions eligible; a single eligible record is chosen without the editor. Edits validate the parent digest, require evidence refs unless `keep_base`, reject `KEEP_BASE` that still contains edits, apply the patch in a temp directory, validate, publish by digest, and allow one retry then fallback to the parent. Completed stages are replayed from the store. Graph recursion limit is `k * 6 + 10` — [controller.py](file:///Users/chamindawijayasundara/Documents/learning_102/google_harness_2_v1.0/.worktrees/implementation/src/harness_clone/controller.py).

Live runs use `DockerExecutor` plus `PiEditor` or `DeepAgentEditor`. `doctor` reports Docker availability and whether the Fireworks key is configured, without printing the key in the source that was read — [cli.py](file:///Users/chamindawijayasundara/Documents/learning_102/google_harness_2_v1.0/.worktrees/implementation/src/harness_clone/cli.py).

### Inferences
- Conventions worth copying for a greenfield Grok harness are a small Python package with an explicit controller graph, content-addressed bundles, a spending cap before any live model call, Docker for execution, replay from stored stage records, and an evaluator that cannot see or write the online run. The kitchen split is controller versus executor versus editor versus offline grader, not one agent that both edits the harness and grades itself.
- Do not copy the Fireworks model pin, Pi worker, or Harness² recursion budgets unless the Grok project is also a harness-optimizer. A coding harness only needs the bundle shape, permission boundary, and separate verification.
- Root gitignore hides the implementation worktree. A new project should keep the runnable tree at the repo root, or document the worktree, so the layout is obvious.

## What does xAI document for Grok tool use, Agents API, or chat completions with tools, as of 2026?

### Takeaway
As of the 2026-10-21 docs fetch, Grok tool use is a client-side function-call loop on the Responses API (`POST /v1/responses`) and the xAI SDK chat helper, plus server-side tools the API runs itself. No separate public Agents API resource was found. `grok-4.7` is the documented flagship for code and agentic tool calling, with a 500k context window.

### Cited Findings
- `grok-4.7` is described as SpaceXSI’s frontier model for coding, agentic tasks, and knowledge work. Documented properties: model name `grok-4.7`; context 500,000 tokens; knowledge cutoff May 2026; text and image input with text-only output; no text output limit; input `$2.00` / 1M tokens and output `$6.00` / 1M tokens; reasoning `low`, `medium`, `high` (default), or `xhigh`; APIs listed as the Responses API; tools listed as function calling, web search, X search, and code execution — [Grok 4.7](https://docs.x.ai/developers/grok-4-7).
- The same page says `POST /v1/responses` for `grok-4.7` always returns `reasoning.encrypted_content`, and multi-turn clients must pass reasoning items back unchanged. It recommends `prompt_cache_key` on the Responses API and the `x-grok-conv-id` header on Chat Completions so a conversation hits the same server. It points long agent loops at context compaction. Grok 4.7 Fast is the same model on faster infrastructure, billed at 2x standard token rates or 1.5x for long-context requests, available only in Cursor and Grok Build, and not on the public xAI API. A US regional endpoint is `https://us.api.x.ai/v1` at a 10% token premium. Grok Build’s default model is this coding agent’s default — [Grok 4.7](https://docs.x.ai/developers/grok-4-7).

### Inferences

## What minimal harness architecture do public coding-agent harnesses share that a greenfield grok-bot needs on day one?

### Takeaway
OpenHands and Claude Code, the two public harnesses checked, both split session state, typed tools, a permission gate outside the model, a workspace, optional sandboxing, narrower subagents, and memory or context compaction. The sibling harness adds an offline verifier that never feeds scores back into the agent. That set is enough for day one. Aider, Goose, and Codex CLI were not separately fetched.

### Cited Findings
- OpenHands SDK docs say the SDK defines agents, LLMs, conversations, tools, workspaces, events, and security policies, and that an agent server runs conversations and tools in a workspace or sandbox. Packages split core SDK, pre-built tools, workspace implementations (Docker, remote), and a multi-user agent server — [OpenHands architecture overview](https://docs.openhands.dev/sdk/arch/overview).
- The OpenHands agent is a reasoning-action loop: query the LLM from conversation history, execute tools, manage context, and validate security before execution. A condenser reduces history near token limits. Skills live in agent context. Each `step()` is one cycle. Tool execution is either immediate or held for user confirmation. The agent is described as stateless, with conversation state as the mutable record — [OpenHands agent](https://docs.openhands.dev/sdk/arch/agent).
- OpenHands tools use a typed Action → Observation contract, a registry, and MCP tools added beside native tools. Annotations include read-only, destructive, idempotent, and open-world hints. The README quickstart wires `TerminalTool`, `FileEditorTool`, and `TaskTrackerTool` to a `Conversation` whose workspace is a directory, and says agents can use the local machine or an ephemeral Docker or Kubernetes workspace via the Agent Server — [Tool system](https://docs.openhands.dev/sdk/arch/tool-system); [SDK README](https://raw.githubusercontent.com/OpenHands/software-agent-sdk/main/README.md).
- OpenHands `TaskToolSet` starts a sub-agent conversation, runs it synchronously to completion, and returns the result so the parent does not keep the sub-task’s context — [Task tool set](https://docs.openhands.dev/sdk/guides/task-tool-set).
- Enterprise OpenHands describes one isolated runtime pod per conversation, with bash, file edits, browser, and git inside that sandbox, and LLM calls through a proxy — [Enterprise architecture](https://docs.openhands.dev/enterprise/architecture). The SDK paper lists event-sourced state, tools, context-window management, a secret registry, and security confirmation as separate components — [OpenHands SDK paper](https://arxiv.org/html/2511.03690).
- Claude Code permissions are enforced by the product, not by the model prompt. Read-only file tools are allowed inside the working directory without a prompt; bash and file modification require approval except a built-in read-only command set. Rules are allow, ask, and deny. Modes include manual, accept-edits, plan (analyze without modifying or executing), auto (a classifier reviews actions), and bypass. A sandboxed bash tool can add filesystem and network isolation. Interactive sessions show a workspace trust dialog — [Configure permissions](https://code.claude.com/docs/en/permissions); [Security](https://code.claude.com/docs/en/security).
- Claude Code subagents each have their own context window, system prompt, tool list, and permission mode. Omitting `tools` inherits the parent tools; listing tools restricts the subagent. A `memory` field points at a persistent directory (`user`, `project`, or `local`). The prompt includes at most the first 200 lines or 25KB of `MEMORY.md`. Built-in Explore and Plan subagents can start without `CLAUDE.md` to stay cheaper. Denying the Agent tool blocks delegation — [Subagents](https://code.claude.com/docs/en/sub-agents); [Create custom subagents](https://code.claude.com/docs/en/subagents).
- The local OpenAI harness README, not an official OpenAI page, lists the primitives that sample uses: a sandbox agent, a manifest for a fresh-session workspace, run config for create/reuse/resume/snapshot, and built-in filesystem editing, shell, skills, memory, and compaction — [open_ai_agent_harness README](file:///Users/chamindawijayasundara/Documents/rnd_2026/open_ai_agent_harness/README.md).
- The sibling keeps verification in `evaluate.py`, which refuses to write inside the online run directory and is documented as never supplied to refinement agents — [evaluate.py](file:///Users/chamindawijayasundara/Documents/learning_102/google_harness_2_v1.0/.worktrees/implementation/src/harness_clone/evaluate.py).

### Inferences
- A day-one Grok coding harness needs these local objects, independent of xAI server tools: a session record (messages, tool calls, reasoning items, `previous_response_id` or SDK chat state, and a stable `prompt_cache_key`); a tool registry whose schemas are object-rooted JSON Schema; a permission check before bash, write, or network, enforced in code; a workspace root plus an optional container; subagent runs as separate sessions with fewer tools; memory files loaded on purpose and not mixed with the hidden grader; and a verifier that runs project tests or exact checks and whose expectations are not mounted into the agent.
- Kitchen-style multi-agent work should copy the sibling’s separation of roles (executor, specialized editors, offline judge) and Claude Code’s per-subagent tool allow-list, not a single shared tool belt. OpenHands shows the parent should see the subagent’s final result, not its full transcript.
- Server-side Grok code execution and web search do not replace local workspace tools or the permission gate.

### Gaps
- Official docs for Aider, Goose, and Codex CLI were not fetched, so this note does not claim their current command names, permission prompts, or memory file formats.
- Claude Code’s exact auto-mode classifier rules and OpenHands’ default confirmation policy for every built-in tool were not fully copied.
- No local project already wires these primitives to `api.x.ai`.
